# 문제 해결 기록

문제가 생겼을 때 어떤 화면부터 보고 원인을 찾았는지 정리했다. 오류 문구만 보는 것보다 실제 파드·저장소·배포 버전을 함께 확인하는 연습이 됐다.

## Grafana만 503이 발생한 문제

### 어떤 상황이었나?

웹사이트와 Argo CD는 접속되는데 Grafana만 503이 발생했다. 브라우저에서 보이는 오류만으로 원인을 판단하기 어려워 파드 상태와 이벤트를 먼저 확인했다.

### 왜 문제가 생겼나?

Grafana의 데이터가 들어 있는 EBS는 특정 가용 영역에 속해 있었다. 노드 자원과 파드 배치도 영향을 주고 있어서 다른 영역의 노드가 늘어나는 것만으로 해결되지 않았다.

노드는 서버이고 파드는 그 위에서 앱을 실행하는 단위다. **앱이 실행될 자리와 기존 디스크를 연결할 수 있는 위치가 함께 맞아야 했다.**

### 어떻게 바꿨나?

노드 그룹을 가용 영역별로 나누고 모니터링 파드의 배치 조건과 자원 설정을 조정했다. 이후 Grafana 파드를 다른 노드로 옮기는 실습을 다시 진행했다.

기존 PVC를 유지하면서 새 노드에서 실행되고 접속도 복구되는 것을 확인했다. **PVC는 파드가 사용할 저장 공간 요청**이므로, 파드 이동과 함께 디스크를 새로 지우는 식으로 처리하지 않았다.

파드 이동 후 복구는 확인했지만 단일 파드와 단일 AZ 디스크 구성이다. 가용 영역 전체 장애에서도 무중단이라고 판단하지는 않았다.

## 새 관리자 비밀번호로 로그인이 안 된 문제

### 어떤 상황이었나?

관리자 비밀번호를 Secret으로 준비했는데 로그인은 계속 실패했다. Secret은 앱에 필요한 값을 전달하는 Kubernetes 리소스다.

### 무엇을 확인했나?

파드마다 실행 중인 이미지 버전과 배포 상태를 확인했다. 새 코드가 아직 준비되지 않아 이전 회원 파드가 요청을 처리하고 있었다.

### 어떻게 해결했나?

새 버전 배포가 끝나고 파드가 Ready가 된 뒤 다시 로그인했다. 비밀번호 준비, 이미지 빌드, 실제 배포 완료는 각각 따로 확인해야 한다는 것을 알게 됐다.

## RDS 생성 실패 원인을 찾은 과정

RDS 생성 요청이 실패했을 때 CloudTrail에서 해당 작업 기록을 확인했다. 비밀번호가 허용 길이보다 길다는 오류가 있었고, 값을 수정한 뒤 생성에 성공했다.

같은 문제가 반복되지 않도록 Terraform에도 비밀번호 길이를 확인하는 조건을 추가했다. CloudTrail을 단순 기록용으로만 생각했는데 오류 원인을 찾는 데도 도움이 됐다.

## 두 파드가 있어도 교체 중 요청이 실패한 문제

프런트엔드를 두 개 실행하고 PDB를 적용했지만, 파드를 축출하는 동안 연속 접속 점검에서 요청 실패가 있었다. 남은 파드 수만 보는 것으로는 충분하지 않았다.

종료할 파드를 ALB가 대상에서 제외할 시간도 고려해 종료 전 대기를 추가했다. 이후 같은 축출 실습에서 두 번째 동시 축출이 차단되고 반복 접속도 정상인 것을 확인했다. 모든 장애에서 무중단이라는 의미는 아니다.

## Windows에서 테스트와 빌드가 달라진 문제

한글 주석이 있는 YAML을 Python 기본 인코딩으로 읽다가 오류가 발생해 UTF-8을 명시했다. Windows에서 건너뛰던 운영 스크립트 테스트는 실행 방식을 보완했다.

빌드 스크립트가 Git Bash 대신 WSL 실행기를 선택할 수 있어 Git Bash를 우선하도록 바꿨다. 실제 사용 PC에서 다시 실행해보는 과정도 필요했다.

## 실행 환경에서 만난 오류

| 문제 | 해결할 때 확인한 내용 |
| --- | --- |
| Terraform 인자·출력 오류 | 모듈 선언과 호출부가 맞는지, 파일을 저장했는지 확인 |
| 설정 파일을 못 찾음 | 실제 Terraform 파일이 있는 폴더에서 실행 |
| PowerShell 스크립트 차단 | 현재 창 범위의 실행 정책을 설정한 뒤 실행 |
| CloudTrail JSON 변환 실패 | PowerShell의 대소문자 키 충돌을 피하도록 Python 사용 |

설정을 바로 더 추가하기보다 이벤트와 로그를 보고 문제 범위를 좁히는 과정이 중요했다.
