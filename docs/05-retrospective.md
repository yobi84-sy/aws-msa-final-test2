# 프로젝트 회고

시스템 엔지니어 관점에서 서비스를 올리는 것부터 배포·확장·알림·복구까지 연결해서 실습해봤다.

처음에는 기술 이름이 많고 어떤 역할을 하는지 잘 구분되지 않았다. 직접 연결해보니 같은 운영 도구처럼 보여도 맡은 일이 달랐다.

- Helm으로 운영 도구를 설치하고 Kustomize로 앱 배포 설정을 관리했다.
- Prometheus로 지표를 모으고 Grafana에서 확인했다.
- CloudWatch가 경보를 만들면 SNS가 이메일로 전달했다.
- CloudTrail에서는 상태 그래프 대신 실제 AWS 작업 이력을 확인했다.

## 실행 중이라는 것과 정상이라는 것은 달랐다

파드가 Running이어도 아직 요청을 받을 준비가 안 된 경우가 있었다. 그래서 **Ready 상태와 실제 홈페이지 접속까지** 확인하는 습관이 필요했다.

배포 때도 코드가 GitHub에 올라간 것, 이미지가 만들어진 것, 새 파드가 실행된 것은 서로 다른 단계였다. 관리자 로그인 문제를 겪으면서 이 차이가 더 잘 이해됐다.

## 서버 수만 늘리면 되는 건 아니었다

노드가 늘어도 파드가 바로 실행되지 않는 상황이 있었다. 필요한 자원과 배치 조건, 디스크가 있는 가용 영역까지 맞아야 했다.

Grafana 문제를 해결할 때는 앱을 다시 띄우는 것보다 어디에 배치되고 어떤 저장소를 사용하는지 확인하는 과정이 더 중요했다.

## 앱은 실습에 필요한 만큼 구성

회원가입·로그인, 상품 등록과 이미지 업로드, 수량 선택·장바구니 주문, 운영자 주문 메일을 구성했다. 관리자 페이지에는 DB 집계와 모니터링·배포 상태를 요약해서 보여줬다.

결제나 배송, 고객별 이메일까지 넓히기보다는 배포와 운영을 확인하는 데 비중을 뒀다. 실제 앱에서 주문한 결과와 운영 도구의 상태가 연결되는 것을 확인할 수 있었다.

## 마무리하며

마지막에는 Terraform 설정이 올바른지 validate로 검사하고, plan에서 추가 변경이 없는지 확인했다. 점검 시점에 두 구성 모두 No changes가 나왔다.

실습 비용을 고려해 NAT 하나, Single-AZ RDS, 일부 단일 파드 구성을 사용했다. 서비스가 복구되는 것은 확인했지만 모든 장애에서 무중단인 시스템을 만든 것은 아니다.

이번 프로젝트에서는 기술을 많이 나열하는 것보다 **각 기술의 역할을 이해하고 직접 동작을 확인하는 것**이 더 중요하다는 것을 느꼈다. 다음에는 운영 알림을 받았을 때의 확인 순서와 복구 방법을 더 정리해보고 싶다.
