# 모니터링과 실습 결과

모니터링은 서비스가 정상인지 계속 확인하는 것이다. 문제가 생겼을 때 화면에서 볼 수 있는 것과 이메일로 알림을 받는 것까지 연결해봤다.

## Prometheus·Grafana·Alertmanager

**지표**는 CPU 사용률이나 Ready 파드 수처럼 상태를 숫자로 나타낸 것이다.

- **Prometheus:** 노드와 파드 등의 지표를 수집한다.
- **Grafana:** 수집한 지표를 그래프로 보여준다.
- **Alertmanager:** 조건에 맞아 발생한 알림을 전달할 대상으로 보낸다.

```text
Prometheus가 지표 수집·알림 조건 평가
  → Alertmanager → SNS → 이메일
```

관리자 대시보드에도 Grafana 연결 상태와 Ready 노드·앱 파드 수를 표시했다. 이 숫자는 Prometheus에서 가져오고 상세 그래프는 Grafana에서 본다.

## SNS — 메시지를 구독자에게 전달

SNS는 메시지가 들어오면 구독 중인 대상에게 전달하는 서비스다. **토픽은 메시지 채널**, **구독은 그 채널의 메시지를 받도록 등록하는 것**으로 이해했다.

내 이메일을 운영 토픽에 구독해서 노드 생성·종료, 운영 경보, 주문 알림을 받을 수 있게 했다.

```text
CloudWatch 경보 / Kubernetes 운영 알림 / 노드 이벤트 / 주문 알림
  → 운영 SNS → 내 이메일
```

SNS가 직접 모든 장애를 찾아내는 것은 아니다. 다른 도구나 앱이 만든 메시지를 전달하는 역할이다.

## SQS — 처리할 메시지를 보관하는 대기열

SQS는 메시지를 보관해두고 처리 프로그램이 가져가도록 하는 큐다. 메시지를 받았다고 바로 삭제되는 것은 아니다. 처리에 성공하면 프로그램이 삭제해야 한다.

삭제하지 않으면 일정 시간이 지난 뒤 다시 받을 수 있다. 실습에서는 같은 메시지를 반복해서 수신하고, 설정한 횟수 이후 **DLQ로 이동**하는 것을 확인했다.

**DLQ는 반복 처리에 실패한 메시지를 따로 보관하는 큐**다. 문제 있는 메시지를 모아서 확인하기 위해 사용한다.

```text
SNS 테스트 메시지 → SQS 수신 → 삭제하지 않고 반복 수신 → DLQ
```

현재 앱의 주문 메일은 운영 SNS에서 내 이메일로 직접 보낸다. SQS 메시지를 처리하는 앱은 구현하지 않았고, SQS·DLQ 경로는 테스트 메시지로 검증했다.

## CloudWatch — AWS 상태를 감시하고 경보 발생

CloudWatch는 AWS 서비스의 지표와 로그를 확인하는 도구다. 이번에는 RDS의 CPU·남은 저장 공간, SQS의 메시지 대기 시간·DLQ 메시지 수를 감시했다.

```text
DLQ에 메시지 발생 → CloudWatch 경보 → SNS → 이메일
```

실제로 DLQ 메시지가 생기자 경보가 ALARM으로 바뀌고 이메일이 왔다. 실습 후에는 테스트 메시지를 삭제하고 경보가 OK로 돌아오는 것까지 확인했다.

## EKS 관리 로그도 따로 확인

EKS의 API 요청·감사·인증 로그를 CloudWatch Logs에 모으고 보관 기간을 설정했다. Kubernetes에 어떤 요청이 들어왔는지 살펴보는 기록이며, 앱의 주문 내용이나 CPU 그래프와는 역할이 다르다.

## RDS 백업에서 데이터를 복원

**스냅샷은 DB의 특정 시점 데이터를 복원할 수 있게 보관하는 백업**이다. 원본과 별도의 비공개 DB를 만들어 검증 데이터가 다시 조회되는지 확인했다. 복원 확인 후 실습 DB와 스냅샷은 정리했다.

원본 DB를 지우고 다시 만드는 방식으로 시험하지 않았다. 백업이 있다는 것과 실제로 복원해서 데이터를 확인한 것은 다른 단계였다.

## CloudTrail — 누가 어떤 AWS 작업을 했는지 기록

CloudTrail은 AWS에서 발생한 API 작업 이력을 남긴다. 누가 언제 어떤 요청을 했고 성공했는지 확인할 수 있다.

RDS 생성에 실패했을 때 이 기록을 확인해 비밀번호 길이 문제를 찾았다. 수정 후 성공 기록도 확인했고 S3에 저장된 로그 파일도 열어봤다.

| 도구 | 확인하는 질문 |
| --- | --- |
| CloudWatch | 지금 CPU가 높거나 메시지가 쌓이고 있나? |
| CloudTrail | 누가 RDS를 만들려고 했고, 왜 실패했나? |

CloudTrail은 고객의 주문 내용을 기록하는 용도가 아니라 AWS 인프라 작업 이력을 확인하는 용도로 사용했다.

## 자동 확장도 구분해서 확인

**HPA는 파드 수를**, **Cluster Autoscaler는 노드 수를** 조절한다. 회원 서비스에 부하를 주고 파드가 늘었다가 줄어드는 것을 확인했다. 노드 수 변화와 알림도 살펴봤다.

**Pending은 아직 파드를 배치하거나 실행할 준비가 끝나지 않은 상태**다. 새 파드가 있다고 바로 노드가 늘어나는 건 아니어서, 자원과 배치 조건을 이벤트에서 함께 확인했다.

## 실습 결과

| 실습 | 확인한 결과 |
| --- | --- |
| 배포 변경 | 새 이미지 반영과 홈페이지 변경 |
| 파드 복구·재배치 | 새 파드 생성, 다른 노드에서 실행, 서비스 접속 |
| 자동 확장 | 회원 파드 증감과 노드 수 변화 |
| 모니터링·메시징 | 대시보드, SNS 메일, SQS 수신, DLQ 이동과 경보 해소 |
| 작업 기록 | CloudTrail의 RDS 생성 실패·성공과 S3 로그 |
| 앱 기능 | 관리자 접근 제한, 장바구니 주문, 주문 메일, 운영 요약 조회 |
| 원격 state | S3 저장·버전 관리·동시 잠금 확인 |
| DB 복원 | 별도 RDS에 검증 데이터 복원 후 실습 자원 정리 |
| 가용성 개선 | 프런트엔드 두 파드, PDB 동시 축출 제한, 종료 대기 후 접속 확인 |
| Terraform | 세 구성 validate 성공, 점검 당시 plan 모두 No changes |
